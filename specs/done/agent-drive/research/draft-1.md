**2. Monorepo Layout**

`apps/web`: Next product shell, auth screens, workspace browser, train/import UI, billing, landing.

`apps/api`: Hono REST API at `service.example.invalid/v1`; owns HTTP shape, auth checks, OpenAPI.

`apps/edge-proxy`: Vercel/fluid-compute proxy for app subdomains, published URLs, custom domains, sync WS upgrades.

`apps/mcp`: hosted MCP server at `service.example.invalid`.

`packages/backend`: Convex schema/domains/crons/auth; metadata source of truth.

`packages/vm-gateway`: in-VM Hono gateway, systemd service, file/memory/session/app/sync endpoints.

`packages/exe-client`: productionized exe.dev client from current `packages/exe-sandbox`.

`packages/duetfs`: CLI.

`packages/api-contract`: shared Zod/types/OpenAPI for REST, CLI, MCP, gateway.

`packages/sync-tunnel`: VM-token WS TCP tunnel adapter for Syncthing.

`packages/test-harness`: docker envs, Convex dev harness, MCP client harness, exe probes.

`packages/billing`: shared micro-USD helpers/constants ported from chat-app registry.

**4. Risks and Scope Firewalls**

The biggest architecture risks are WS support on Vercel fluid compute, Syncthing over the edge tunnel under load, exe custom-image mechanics, and `cp` snapshot consistency on running VMs. Slice 0 must retire or reshape these before feature work.

Single-owner invariants: Convex owns metadata; VM disk owns file truth; `@duetso/agent` owns memory SQLite; Anchor owns path identity; Audit owns provenance; edge owns URL routing/tunnels; gateway owns in-VM process supervision.

Never sync `.duet/` or memory DB. Never rely on raw TCP between VMs. Never treat Syncthing receive-only as security; enforce read-only with filesystem permissions. Never let public URL access bypass folder access checks.
