## Read this first: two claims in the old handoff are wrong

1. **Leg 1 does not pin an agent version.** It asserts only that an agent and
   gateway version are PRESENT (`staging-e2e-synthetic`, the
   `versions` leg). The old doc's "must report `agentVersion: 0.3.7`" describes
   intent, not the assertion. Staging runs **0.3.8** on every active workspace,
   and the repo pins `@duetso/agent` 0.3.8 with no env override.
2. **A post-switch `balanced` attribution is NOT proof of a stale runner.** The
   old doc calls it "a real regression, not flake". The assertion is racy — see
   below — so it cannot distinguish the two.

## What is settled about the design

**A tier change must take effect on the NEXT turn, never mid-turn** (Example User,
2026-07-31). Mid-turn switching is explicitly unwanted.

The shipped mechanism already matches that, and it is worth stating plainly
because it is easy to re-derive wrongly:

- `duet-agent` knows nothing about tiers. It implements **virtual models**.
  Tiers are purely a Duet concept, mapped to a virtual model name at the
  boundary.
- A tier reaches the agent exactly once: the `--model <tier>` spawn flag
  (`packages/gateway/src/runner/process-runner.ts`).
- The RPC process lives for **one turn** — *"The process exits as soon as that
  terminal lands"* (`@duetso/agent/dist/src/cli/rpc.js`). So the next turn is a
  new process, spawned with whatever tier the new request carried
  (`coordinator.ts`, the relaunch branch of `deliver`).

Spawning IS the per-turn switch. Nothing else is needed, and the `tier` field
that used to ride on the agent's prompt command has been **deleted** — the agent
never declared it, never read it, and it could only ever have meant mid-turn
switching.

## The open question — ANSWERED, kept for its reasoning

**Answered 2026-08-01: real product bug.** The analysis below of *why the
assertion could not be trusted* was correct and is what made the verdict
collectible; only its "not established" conclusion is superseded.

Leg 5 fails live with the follow-up generation attributed `balanced`. Whether
that is a product bug or a test artefact is **NOT ESTABLISHED**.

The assertion is racy by construction. `waitForFirstTieredGeneration` takes the
**oldest** new tiered generation (`listGenerationsForTest` is `.order('asc')`,
then `.find`), and it returns as soon as the FIRST generation settles. A tier's
closure spans several models — *"direct route targets + vision fallbacks +
ENABLED advisor targets + the shared classifier + the internal memory and
embedding models"* (`packages/contract/src/model-tiers/index.ts`) — so one turn
can produce several generations. Any `balanced` generation created after the
`generationsBeforeMax` snapshot is found first and fails the assert, whether or
not the switch worked.

`gatewayGenerations` rows carry no session or turn id (`schema.ts`), only
`workspaceId` and `createdAt`, so turn attribution is by time alone. That is the
root of the fragility.

**The one artefact that settles it** is the `fresh=` dump already wired into the
assertion message: every new tiered generation with its tier, model, status and
createdAt.

- only `balanced` rows → the switch genuinely did not take effect.
- `balanced` then `frontier` → a late generation from the previous turn; the
  product is correct and the assertion needs rewriting to "a `frontier`
  generation appears, and nothing after it reverts".

## What blocked collecting it (historical)

**The journey cannot reach leg 5.** 8 of 11 runs on 2026-07-31 died earlier,
most with `Standard session did not reach a terminal event` and the rest with a
transport timeout on the long-lived SSE read.

The sessions are wedged at `lastEventSeq=2` — `session_created` + `user_prompt`,
no `turn_started`, no steps, no terminal. The agent produced nothing.

Scope, measured rather than assumed: **every wedged session belongs to a
`virtual-model-tiers-staging-e2e-synthetic*` workspace.** Other staging sessions in the
same window completed normally (one `complete`, one `sleep` with 88 events). So
this is not staging-wide breakage — it is specific to this journey's fresh VMs,
which is a much narrower and more tractable problem.

A gateway-log capture is now wired into the failing assert (`tiersGatewayLog`),
using the internal-admin log route with a `<runId>-user@example.invalid` identity. Its
first run returned `<no agent lines>` from a keyword filter; the filter has been
replaced with a raw tail, and that run had not completed when this was written.
**That raw tail is the next thing to look at.**

## Cheap wins for whoever picks this up

- The SSE read has no transport-level timeout headroom; `GENERATION_WAIT_MS` is
  300s but the fetch underneath gives up first with `The operation timed out`.
  Worth a look before blaming the product.
- `login-as` with `create: true` PROVISIONS A WORKSPACE. Ledger any identity you
  mint, and use the `<runId>-user@example.invalid` shape —
  `assertStagingE2ESyntheticEmail` refuses to reap anything else, so an invented
  address leaks a workspace and VM that cleanup is not allowed to touch.

## The wedge probe

`assets/probe-wedge.ts` reproduces the leg-5 wedge (fresh e2e VMs stop at
`[session_created, user_prompt]` with no `turn_started`) and captures the
gateway log. It lives in this spec folder rather than `packages/test-harness/src`
because it is a one-off diagnostic, not a harness surface — it has no callers and
tripped the lint gate there. Run it from `packages/test-harness`:

```
bunx dotenvx run -f ../../.env.staging -- bun ../../specs/done/virtual-model-tiers/assets/probe-wedge.ts
```
