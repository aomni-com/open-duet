Train records during training — retryable busy state

Refreshing the train page mid-training 502s the memory library. This map records everything the walk settled: the diagnosis, ten closed decisions, the extracted taste, and the landmines — plus the tweakable plan and a paste-ready build prompt.

Q1 · Known knownsThe settled ground

  • Diagnosis (evidence-closed): the trainer holds the PGlite memory DB's exclusive open-lock; duet train list --wait 5 exits 75 after 5s; the gateway maps any non-zero exit to 502 train_command_failed (packages/gateway/src/train-runner.ts:147); the api proxies verbatim (apps/api/src/routes/train.ts:89). Confirmed in the VM's ~/.duet/logs/gateway.log: 502s with ~7s duration during the job, 200 the moment it finished.
  • Exit 75 is already a contract on both sides: duet-agent's failMemoryLockTimeout (cli/memory-db.ts:29) and this repo's MEMORY_CLI_CONTRACT.exitCodes.lockTimeout (contract/src/memory/index.ts:85). No duet-agent changes needed.
  • The target pattern already ships: memory routes map exit 75 → 503 memory_lock_timeout (gateway/src/routes/memory.ts:132) — and that behavior is already public via /v1/ws/:slug/memories* (api/src/routes/workspaces.ts:326,337).
  • The 5s was a placeholder: introduced in agent-drive slice 06 (f063819) against a mocked CLI, before PGlite lock semantics existed. Never tuned; today's incident is the first contention data.
  • Web: react-query is retry: false globally (spa/root.tsx:58); apiError() surfaces the body's error as DuetApiError.code; the page already refetches records on job completion (train.tsx:77-85).
  • Every train command runs behind the pin rail: ensurePinnedRunnerBinary (gateway/src/runtime/http.ts:438) guarantees the pinned duet version before spawning.
  • Rollout: gateway release rail (self-announcing) + Vercel web deploy. No VM image rebuild, no npm publish, no api change.

Q4 · Unknown unknownsLandmine cards

Trainer shares the 5s wait — training start can fail the same way closed → decision #9

Evidence: runtime/http.ts:434 feeds the same waitMs into the pipeline; train/duet-cli-runner.ts:12 forwards it to duet train. Bumped to 30s.

react-query retry-vs-poll trap sharp edge

Implementing the poll via retry would keep the query out of error state and the banner would never render. Must be a refetchInterval callback on query.state.error; a test pins that v5 polls errored queries.

Unified classifier must not regress not_found sharp edge

Exit-code classification first (75 → busy); stderr matching stays for not_found → 404. The capability branch is deleted per decision #10. Memory routes' 502 body (exitCode, message) preserved.

Five test assertions encode the old 502 sharp edge

gateway.test.ts:3436/3696/3778/3821/4012 + the fake CLI in records.test.ts needs an exit-75 mode. gateway.test.ts:3495 is the pattern to extend.

capabilityVersion removal has a skew window sharp edge

Old web validates z.literal(1); a new gateway that stops sending it breaks records listing until the web deploy lands (minutes). Accepted under no-backward-compat.

Agent's in-VM memory writes block during training OPEN

During a training, duet-agent's own writes wait on the same lock with its 30s in-process budget. duet-agent-side concern; unblocks when that repo takes a pass. Not touched here.

"Training in progress — memories refresh when it finishes." / "Memory is busy — refreshing shortly." Tweak freely; es-419 machine-translated to match.
