# Live Apps

Live apps let a later conversation change an app's data and show the result in
an already-open session pane. The platform supplies discovery and a durable
public transport boundary; each app owns its API, data, events, and UI.

## Why this shape

Changing an app's data and changing the app itself are different jobs. A
builder edits source through the drive. A chatting agent reads the app's README
and calls its VM-local HTTP API. Keeping that distinction explicit prevents a
request such as “add a task” from becoming a source edit that hard-codes the
task.

The agent already receives the registered app list, including each configured
port. Rendering `http://192.0.2.1:<port>` into the generated app guidance is
therefore enough for discovery. A new app wire field, filesystem scan, README
marker, or platform notification service would create another owner without
unlocking behavior. The renderer remains pure and byte-deterministic; the app
README remains the app-specific contract.

The app pushes its own changes with standard server-sent events. This keeps the
platform out of application state and lets the same API serve agents and human
clients. The public edge turns an unbounded app stream into hosting-safe
segments, while the browser's native `EventSource` reconnects. Applications do
not implement platform-aware retry loops.

The shipped Hello task list is intentionally a small worked example rather than
a framework. It uses atomic JSON so the example has no dependency or
replicated SQLite sidecars; this choice does not redefine storage policy for
all apps. No platform contract depends on Hello's task routes, task schema, or
`tasks.json` filename. The implementation-time calls are preserved in the
[`choices ledger`](choices.md).

## Invariants

- `yourAppsPrompt` is the sole discovery owner. It renders the configured
  loopback address but never exposes runtime commands or API scopes. It tells
  agents to read the app README first and narrate data changes afterward.
- Data-versus-source is an agent contract, not a platform permission boundary.
  The prompt and app README direct chatting agents to the API; acceptance pins
  the intended behavior by hashing Hello's complete source tree around a
  later-session mutation and excluding only its exact runtime data path.
- The builder contract for a live app is ordinary HTTP reads/writes plus
  `text/event-stream`, a heartbeat below Bun's idle timeout, request-abort
  cleanup, and native `EventSource` retry. Each app decides whether frames are
  invalidation nudges or a replayable log; the platform does not inspect or
  persist application events.
- The shipped Hello example is deliberately stricter than the minimal builder
  reference: it commits before announcing, emits task ids, and removes writers
  on request abort, stream cancellation, or enqueue failure.
- Builder guidance treats WebSockets as unsupported and selects SSE. The edge
  can forward upgrade headers, but this work establishes no functional or
  lifecycle contract for app WebSockets.
- Only app responses declared as `text/event-stream` receive the edge's
  four-minute segment policy. Pages, downloads, mutations, and publishes keep
  normal pass-through behavior.
- Cancellation follows the HTTP request across browser → edge → gateway → app.
  There is no cleanup side channel or app-writer registry in the platform.
- Native `EventSource` owns reconnect. The edge closes while its invocation can
  still cancel upstream work. The platform neither stores nor replays app
  events; an app that needs gap-free delivery owns revalidation or replay, but
  still uses native browser retry rather than platform-specific retry code.
- The rollout is a hard cutover for newly seeded workspaces. Existing apps and
  existing workspaces are not migrated or swept.
- The HTTP and browser staging proofs have separate owners. `build-app` proves
  a generated app through the public edge; `session-app-pane` proves discovery,
  narration, source stability, DOM liveness, and no reload in a real pane.

## What the build taught us

The recorded first deployed stream test disproved the assumption that passive
response streaming was sufficient. Its report says incremental bytes reached
the browser for 300.263 seconds, then the hosting boundary ended the edge
invocation; native reconnect never reached the app and abandoned writers
remained open. Waiting for the hard limit longer, or merely increasing it,
preserves the same owner-boundary failure.

The localized repair is a proactive edge-owned close with request cancellation
forwarded across both proxy hops. The repaired-run report records a 240.492-second
close, `Last-Event-ID` reconnect after 4.302 seconds, stable documents, and zero
remaining writers. The generated-app journey summary separately records a
240.843-second segment and a 1.229-second reconnect frame. The before/after
report is preserved in
[`research/live-app-sse-probe.md`](research/live-app-sse-probe.md).

The browser proof also exposed an acceptance-oracle mistake. Curl's `-d`,
`--data*`, and `--json` forms perform a POST without spelling the word `POST`,
and valid narration need not repeat a synthetic marker. Durable history now
requires a successful tool-call reference to the app-specific README, followed
by the exact loopback URL and marker with POST semantics, then a non-empty reply.
Iframe content independently proves the exact mutation. This keeps the gate
behavioral without claiming to inspect shell output or coupling it to prose style.

## Rejected alternatives

- **Bounded polling:** it would weaken the push-based freshness contract and
  make every app pay for a platform lifecycle bug. The localized edge repair
  proved standard SSE viable.
- **Manual browser retry:** reconstructing `EventSource` in each app duplicates
  platform behavior and makes apps aware of the hosting boundary.
- **A central notification rail:** the platform would become a second owner of
  application events and state.
- **A new app schema field or README marker:** the registered port and
  unconditional README instruction already provide discovery. Extra schema or
  filesystem state would add migration and cache invalidation surface.
- **Waiting for platform termination:** the original live probe showed that the
  hard cutoff cannot be trusted to run upstream cleanup.
- **SQLite in the seed example:** replicated WAL/SHM churn obscures the lesson;
  atomic JSON keeps this particular example inspectable and dependency-free.
