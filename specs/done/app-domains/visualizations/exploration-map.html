App domains

Exploration map · September 30, 2026 · Historical exploration captured before implementation.

Historical requirement context: the shipped App domains rationale records the final behavior and evidence. Later user decisions: no legacy migration; aomni.co is authorized for testing; every embedded app stays on the Duet host, whether public or private. The observations below describe the code at exploration time.

1. Known knowns

Port the previous chat-app feature into Duet’s workspace/app architecture. The reference provides add, DNS instructions, conflicts, automatic verification, manual recheck, and removal through Vercel. Sources: reference actions, Vercel client, and management UI.

At exploration time, Duet had no custom-domain table, backend implementation, or UI. An unused state-machine contract survived. Its edge parser rejected custom hosts. The app resolver already owns visibility, authorized folder access, workspace availability, and origin resolution.

3. Unknown knowns — extracted intent

  • The feature should be simple: one domain slot per app, no multi-domain management or primary-selection system.
  • Custom domains are the address users share, but existing Duet links must remain useful.
  • The settings label is specifically App domains.
  • Private-app sign-in is an improvement to apps generally, not a feature restricted to custom domains.
  • Human users manage through the app menu or workspace overview; agents retain programmatic management. Target environments are Duet’s existing staging and production edge deployments.
