# Implementation choices

These are the final decisions made where the requested behavior left a gap.
Model access, effective text defaults, direct at-cost billing and MCP model-choice
parity are requirements, rather than discretionary choices.

## Image capability lookup

**When:** MCP parity and closeout review.

**Decision:** Before any image request, resolve an existing role locally and read
upstream capability metadata with a bounded, best-effort request. A language model
uses the language SDK operation; absent metadata leaves native image generation.
This includes role-based calls. The alternative was to skip discovery for roles
or infer the operation from provider names.

**Gap:** A local image role describes the output kind, not whether the upstream
generator uses a language or native-image operation.

**Rationale:** Upstream owns capabilities. Keeping operation facts in another
local registry would drift; treating discovery failure as denial would rebuild
an access gate the feature removes.

**Consequence:** Image roles gain one unbilled metadata read and its possible
latency. Exact resolved IDs, existing defaults and durable output links remain.
A metadata outage can still leave an image-producing language model on an
unsupported native operation; the caller receives that failure without a model
substitution.

## Paid automation controls

**When:** client implementation and acceptance design.

**Decision:** Expose an optional CLI retry count and optional MCP video duration
and resolution. Omission preserves existing defaults. The alternative was to
change retry behavior globally or hide request controls in the test transport.

**Gap:** The acceptance plan bounded paid attempts and video size, while the
existing CLI allowed SDK retries and MCP could not express those video controls.

**Rationale:** Automation should state its limits through the same supported
client surface other callers use. A test-only video request would bypass the
contract under acceptance.

**Consequence:** These additive inputs become supported client grammar. They do
not imply full CLI/MCP parameter parity or a strict final-cost ceiling.

## Acceptance execution and ownership

**When:** staging journey implementation.

**Decision:** Invoke the built standalone CLI directly and use the official MCP
client. Choose uncatalogued media from upstream prices whose conditions can be
selected by the request. Guard each CLI child against a second model POST.
The alternatives were an intervening paid agent, hard-coded provider choices,
or assuming conditional audio/quality prices applied to an unconfigured request.

**Gap:** Existing agent-driven journeys buy extra model calls, and upstream video
price modes do not always match the controls this request can express.

**Rationale:** Direct client execution proves the requested surfaces without
buying intermediary work. Capability/price selection keeps the probe usable as
providers change, and the transport guard detects a hidden retry before spending.

**Consequence:** The focused journey fails before generation if discovery cannot
supply a suitable probe. Its receipt joins generated bytes to terminal actual-cost
accounting; output alone never establishes success.

**Decision:** Give verified teardown its own budget and remove only resources in
this journey's ledger. Inspect the global ephemeral sweep in list-only mode.
The alternative was to let acceptance timeout also end cleanup, or delete every
VM carrying the shared ephemeral tag.

**Gap:** Other sessions can run staging journeys concurrently.

**Rationale:** The existing ledger knows exact ownership. A shared tag cannot
distinguish this run's resources from someone else's active fixture.

**Consequence:** Timed-out acceptance still cleans up, and unrelated journeys
keep running. Broad deletion remains a separate operator action.

## Failure accounting before cleanup

**When:** live acceptance repair.

**Decision:** A failed output waits, within a separate bounded accounting budget,
for the already-started generations to settle or release before teardown. The
alternative was immediate deletion of the payer whenever a client returned an
error.

**Gap:** A provider can complete and incur cost while a later SDK download fails.
Client failure alone does not establish whether accounting has finished.

**Rationale:** The backend remains the accounting owner. Reusing its generation
state and the existing progress wait avoids inventing cancellation or deleting
the account out from under settlement. Retriable charge/upstream failures remain
pending for this purpose.

**Consequence:** Failure cleanup can wait for settlement; timeout records missing
accounting evidence and still retains the resource teardown rail. Acceptance never
silently converts that missing evidence to success. A probe that empirically
rejects the selected controls can be excluded from this test's candidate pool;
that exclusion does not change production model discovery or access.
