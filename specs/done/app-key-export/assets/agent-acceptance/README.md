# Controlled agent acceptance

Two fresh agents received only the authored build-app skill, the request to
build a Vercel app using Duet AI, and authenticated loopback tools. Their actual
server handlers ran under the host's server environment. The fixtures modeled
workspace app-management authority and separated build, runtime API and gateway
origins; production services and member content were never used.

Both operation oracles passed. The new-app agent registered a tracking page,
exported once, configured all returned settings through stdin, then deployed.
The existing/full agent preserved the row, inspected safe inventory, retired
an explicitly unused credential to free capacity, deployed a replacement and
revoked the old active credential only after validation. Neither asked for
human Duet key setup or persisted/disclosed credential values. The safe receipts
and operation files retain IDs, ordering and booleans only.

T3's collaborative browser captured the new tracking page in both themes at
1280px and 400px CSS widths. Mobile snapshots have DPR2. No earlier appearance
exists, so scene metrics provide absolute sparse-page telemetry rather than a
before/after fidelity claim. An unprimed visual reviewer inspected all four
shots: no blockers; text, hosting status, purpose and external link are clear,
with no clipping or horizontal overflow. The fixture-generated plain blue icon
is cosmetic and is not a proposed production asset. Browser DOM inspection
confirmed the actual deployment link uses a new tab and noreferrer.

This proves the teaching workflow with controlled tools, not live Vercel or
NewEra. Staging owns deployed platform and runtime availability. The oracle
fixtures were scratch tools and are not another shipping staging framework.
